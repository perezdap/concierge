Concierge → Production Readiness Plan

From working MVP (68/100) to a hardened, deployable gateway  ·  mcp-gateway-p

Companion to the comparative review · 2026-05-29 · This plan turns the review findings plus the project's own docs/ROADMAP.md into a sequenced, acceptance-criteria-driven work plan. Items are tagged SECURITY where they are exploitable, NEW where the review surfaced them (not in the existing roadmap), and PLANNED where they extend the author's roadmap.

Where it stands today. A genuinely working MVP: clean inward-pointing layers (core / adapters / gateway / policy / server / util), a faithful catalog→publish→callable→blocked model, best-in-class upstream-metadata sanitization, packaging with a console entry point, 20 passing tests, and good docs. What blocks production: two exploitable security bugs, an approval broker that bricks all gated tools, hand-rolled protocol gaps, resource leaks, in-memory-only state (no horizontal scale), no real auth/observability/deploy story, and zero test coverage on the riskiest layers (facade + adapters).

Definition of "Production Ready"

This plan targets a concrete bar. The gateway is production-ready when it can be exposed to real clients in front of untrusted upstreams and meet all of the following exit criteria:

SecurityNo known auth/origin bypass; constant-time secret comparison; TLS-terminated; secrets sourced from env/secret manager, never files; security scan (bandit + pip-audit) clean in CI. ProtocolPasses a conformance harness: version negotiation, correct 202-for-notifications, header validation, batch handling, error envelopes. ReliabilityNo unbounded queues or leaked sessions; graceful drain on SIGTERM; upstream failure isolation with backoff + circuit breaker; survives a soak test. ScaleStateless app tier — catalog + sessions in a shared store (Postgres/Redis) so N replicas run behind a load balancer. Operability/metrics (Prometheus), OpenTelemetry traces, structured + sinkable audit log, /healthz + /readyz, runbook. Quality gateCI runs lint (ruff) + type-check (mypy) + tests with ≥80% coverage incl. facade/adapter integration tests; reproducible Docker image; pinned deps. DocsNo docs/code drift; deploy guide; operator runbook; threat model documented.

P0  Blockers & Bug Fixes (≈ 1.5–2 weeks)

These are correctness/security defects found in review. None are in the existing roadmap, and every later feature sits on top of them. Each is small in isolation; the value is shipping them as a hardening sprint with tests that lock the behavior.

SECURITYP0-1 · Fix the origin allow-list bypass~0.5 day

facade.py:47 uses origin.startswith(a), so http://localhost.evil.com passes against an allow-list of http://localhost — a DNS-rebinding vector. Also decide policy for Origin: null/missing (currently allowed unconditionally), since null is what sandboxed pages send.

Done when: origin matching is exact (scheme+host+port, parsed via urllib.parse); a test asserts localhost.evil.com and null are rejected unless explicitly allow-listed.
SECURITYP0-2 · Constant-time token check + stop leaking token bytes~0.5 day

auth.py:36 compares bearer tokens with not in (timing oracle). auth.py:38 logs token[:6] into the audit subject.

Done when: comparison uses hmac.compare_digest against hashed tokens; audit subject uses an opaque token id / SHA-256 prefix of a salted hash, never raw token bytes.
NEWP0-3 · Unbrick the approval path~1 day (interim)

The only registered broker is DenyByDefaultApprovalBroker (always False, app.py:133 / approval.py:22), so every requires_approval/dangerous tool is permanently uninvokable. Interim fix now; full workflow is P1-3.

Done when: a config-selectable broker exists (e.g. AllowListApprovalBroker or pre-approved-tool config) so gated tools can be invoked under an explicit operator decision; default stays deny but is documented as such.
NEWP0-4 · MCP protocol conformance~3 days
  • Negotiate protocolVersion instead of hard-coding 2025-06-18 (service.py:74): echo the client's version if supported, else the server's best, else error.
  • Return 202 Accepted, empty body for notification-only POSTs (currently 200 + null, facade.py:136–164).
  • Validate the MCP-Protocol-Version request header; handle JSON-RPC batch arrays.
  • Fix the facade docstring that promises an SSE response body it never returns.
Done when: a conformance test suite (or the official MCP test client) passes for initialize/notify/list/call across supported versions. Strongly consider adopting the official mcp Python SDK to retire the hand-rolled JSON-RPC layer entirely — this also future-proofs spec changes.
NEWP0-5 · Resource-safety fixes (leaks & deadlocks)~2 days
  • Bound per-session notification queues (currently unbounded → memory leak per idle session); drop-oldest or backpressure policy.
  • Schedule SessionManager.gc — it exists but is never called; sessions accumulate forever. Add a periodic task + idle TTL.
  • Drain stdio stderr (stdio.py:58): a chatty child fills the pipe buffer and deadlocks. Add a stderr reader that logs.
  • Fix cross-chunk SSE parsing (streamable_http.py:120, sse_legacy.py:100): buffer across network chunks instead of assuming each data: line is whole.
Done when: a soak test (1k sessions, chatty stderr, fragmented SSE) shows flat memory and no dropped/garbled messages.
NEWP0-6 · Close docs/code drift + config gaps~1 day
  • Implement ${VAR} env-templating in load_config (config.py:89) — it's documented and used in the example YAML but doesn't exist (secrets are passed through literally).
  • Either implement or remove the doc claims for exp-backoff reconnect and callable=false marking (ARCHITECTURE.md promises both; neither exists). See P1-5 for the real implementation.
  • Remove dead code: log.py:39 log_event; reconcile primitives.py:107 (names=="*" vs array schema); drop the unnecessary runtime __import__ in app.py:117.
Done when: every feature stated in docs is backed by code or the claim is removed; env-templating has a test; no dead/unreferenced functions.
NEWP0-7 · Quality gate: CI + test the risky layers~3 days

The 20 existing tests cover pure core logic well but the facade (auth/origin/session/error-mapping) and real adapters (stdio/http/sse framing) have zero coverage — exactly where the bugs live.

  • Add facade integration tests (TestClient): auth accept/reject, origin reject, batch, notification→202, error envelopes.
  • Add adapter framing tests with fake upstreams (stdio newline framing, SSE chunk-boundary, circuit-breaker trip/reset).
  • Stand up CI: ruff (lint) + mypy (type-check) + pytest --cov with an ≥80% gate + bandit + pip-audit.
Done when: CI is green on every PR, coverage ≥80%, and each P0 fix above ships with a regression test.

P1  Production Foundations (≈ 4–6 weeks · maps to the author's Phase 2)

With P0 done, the gateway is correct but still single-process and lab-grade. P1 makes it deployable, scalable, secured, and observable. Most of this is the project's own Phase 2 — sequenced here with operability and deploy work folded in.

PLANNEDP1-1 · Real authentication~1 week

Replace static bearer tokens with pluggable AuthProviders: OAuth2/OIDC (any IdP that issues verifiable id_tokens), mTLS pass-through for service-to-service, and per-tenant token issuance + revocation list.

Done when: a request is authenticated against a real IdP in an integration test; revoked tokens are rejected; auth provider is config-selectable.
PLANNEDP1-2 · Persistent, shared state (enables horizontal scale)~1–1.5 weeks

Implement SQLiteCatalogStore and PostgresCatalogStore behind the existing CatalogStore ABC, with a migration runner; add a Redis-backed session store as a drop-in for SessionManager. This is the single biggest lever — the layering already supports it, so the app tier becomes stateless.

Done when: two app replicas behind a load balancer share catalog + sessions; killing one replica mid-session is transparent to the client.
PLANNEDP1-3 · Real approval workflow~1 week

Replace the P0-3 interim broker with a queue-backed ApprovalBroker: pending approvals surfaced as MCP resources clients can poll, an operator decision path, and webhook callbacks on grant/deny.

Done when: a dangerous tool call parks as pending, an operator grants it out-of-band, and the original call resumes — end-to-end test.
PLANNEDP1-4 · Distributed rate limiting~3 days

Move the in-memory token bucket to a Redis-backed distributed limiter keyed by (tenant, session, tool), with per-tenant quotas and a 429-equivalent error carrying Retry-After.

Done when: limits hold consistently across replicas; load test confirms enforcement + correct backoff signaling.
NEWP1-5 · Upstream resilience (deliver on the doc claims)~3 days

Implement what ARCHITECTURE.md already promises but the code lacks: exponential-backoff reconnect for dropped upstreams and callable=false marking of catalog entries when their upstream is down (so a flapping server degrades gracefully instead of silently shrinking the catalog).

Done when: a killed upstream reconnects with backoff; its tools show as non-callable rather than vanishing; a client gets a clear error, not a hang.
PLANNEDP1-6 · Observability~1 week

OpenTelemetry traces spanning gateway → adapter → upstream; a Prometheus /metrics endpoint (request rate, latency, upstream health, circuit-breaker state, queue depth); a pluggable audit sink interface (Kafka / S3 / OpenSearch) on top of the existing redacted audit stream; add /healthz + /readyz.

Done when: a single tool call produces an end-to-end trace; dashboards show golden signals; audit events land in an external sink.
NEWP1-7 · Deployment & lifecycle~3 days
  • Reproducible, pinned Docker image (multi-stage, non-root); pin/lock all deps (currently floor-pinned only, e.g. fastapi>=0.110).
  • Graceful drain on SIGTERM — stop accepting new sessions, finish in-flight calls, close adapters cleanly (the lifespan hook is a good start).
  • TLS termination guidance (reverse proxy / ingress); config via env + secret manager, never committed files.
  • Sample k8s manifests / compose with liveness/readiness probes wired to P1-6.
Done when: docker run + a rolling restart drops zero in-flight requests; image passes a vuln scan; no secret ever touches disk.
PLANNEDP1-8 · Output filtering & caching~4 days

An OutputFilter chain on upstream results (PII scrubbing, secrets detection, length caps, content-type allow-lists) — the response-side complement to the existing input sanitization. A CachingAdapter decorator with per-tool TTL for idempotent read tools.

Done when: a tool returning a fake secret has it redacted before reaching the client; a cached read tool serves a second identical call without hitting the upstream.

P2  Scale & Enterprise (post-launch · maps to the author's Phase 3)

Not required for a production launch, but the natural follow-on. These are largely the author's Phase 3, which is sound — listed here for completeness and sequencing.

P2-1 · Multi-tenant policy

ABAC TenantPolicyEngine with per-tenant catalog views (tenant A sees only its upstreams). Depends on P1-1/P1-2.

P2-2 · Admin UI

Live catalog browser, session inspector, audit search, approval review — built on the existing /admin/* JSON endpoints.

P2-3 · High availability

Primary/replica failover per upstream, configurable session affinity for sticky routing. (Graceful drain already lands in P1-7.)

P2-4 · Tool-poisoning defense in depth

Cross-source duplicate-name quarantine, heuristic instruction-leak detector on descriptions, operator description overrides. Extends the strong input sanitization.

P2-5 · Resource & prompt parity

Streaming resource passthrough, notifications/resources/updated propagation, prompt-argument validation at the boundary.

P2-6 · Advanced caching / quotas

Leaky-bucket option, per-tenant quotas, smarter cache invalidation — builds on P1-4/P1-8.

Suggested Sequencing

Single-engineer estimate; parallelizes well across two. P0 ships as one hardening release; P1 as a "production beta"; P2 post-GA.

Milestone 0 — Hardening release (weeks 1–2)
All of P0. Outcome: correct, secure-enough-to-pilot, CI-gated. This is the prerequisite for everything; do not start P1 features on top of unfixed P0 bugs.
Milestone 1 — Stateless & secured (weeks 3–5)
P1-1 (auth), P1-2 (persistence/shared state), P1-5 (resilience). Outcome: multi-replica behind a load balancer with real auth.
Milestone 2 — Operable & governed (weeks 6–8)
P1-3 (approval), P1-4 (rate limiting), P1-6 (observability), P1-7 (deploy), P1-8 (output filtering). Outcome: production beta meeting the exit criteria above.
Milestone 3 — Enterprise (post-GA)
P2 items as demand dictates (multi-tenant, admin UI, HA failover, deeper poisoning defenses).

Realistic effort to the production-beta bar (Milestone 2): ~6–8 engineer-weeks for one engineer, less with two working P0 + test infra in parallel. This is hardening on strong bones — not a rewrite.

Key Risks & Decisions

  • Adopt the official MCP SDK or keep hand-rolling? The hand-rolled JSON-RPC works but every spec change is manual and conformance bugs (P0-4) recur. Recommendation: adopt the SDK during P0-4 while the protocol surface is already open — highest-leverage decision in the plan.
  • State store choice (P1-2) gates scale. Postgres for catalog + Redis for sessions is the conventional split; doing it early keeps the app tier stateless and avoids a painful retrofit. This is the most architecturally consequential P1 item — sequence it before approval/rate-limit which both assume shared state.
  • Security items are not optional polish. P0-1/P0-2 are exploitable today; the gateway must not be exposed beyond loopback until they land (the existing __main__ loopback rail enforces this — keep it).
  • Test debt is concentrated exactly where the bugs are. P0-7 (facade/adapter tests + CI) should run alongside, not after, the P0 fixes so each fix is locked by a regression test.

This plan incorporates the project's own docs/ROADMAP.md (Phases 2–3) and supersedes its ordering only by inserting the P0 bug/security fixes ahead of feature work, since several were not captured there. Effort figures are engineering estimates for planning, not commitments.
